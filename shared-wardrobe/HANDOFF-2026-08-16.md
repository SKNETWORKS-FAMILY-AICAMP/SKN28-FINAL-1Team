## 2. 왜 바꿨나

등록 화면에서 **'공유 옷장' 토글**을 켜면, 그 방 선택값이 **기기 저장소(`secureStore`)** 에 `{아이템id: 방id}` 로 저장됐다가 사용자가 옷을 확정할 때 공유되는 구조였다. 문제 셋:

| 문제                                                    | 결과                                                                   |
| ------------------------------------------------------- | ---------------------------------------------------------------------- |
| 예약이 기기에만 있음                                    | PC 에서 올리고 폰에서 확정 →**공유가 조용히 누락**              |
| `redeemShareReservation` 이 `catch { return null }` | 실패 사유(방 나감 / 네트워크)를 구분 못 하고 사용자에게 아무 안내 없음 |
| 공유 상태가 항상`available` 고정                      | "올려는 두되 아직 안 빌려줌"을 고를 수 없음                            |

→ **예약을 서버 컬럼으로 옮기고, 소진을 확정 API 안에서 처리**하도록 바꿨다.

### 설계 판단: 공유 관계 자체는 조인 테이블 그대로 둔다

`wardrobe_item` 에 방 id 하나만 넣으면 안 된다. `uq_shared_wardrobe_item_room_item` 이 (방, 옷) **쌍**에 걸린 유니크라 **한 옷이 여러 방에 들어갈 수 있고**, 방마다 `status`·`registered_by`·`created_at` 이 따로 있다. 컬럼 하나로 접으면 이게 다 사라진다.

**예약만** 옷당 최대 1건·확정되면 소멸하는 임시값이라 FK 컬럼이 맞다.

## 4. 동작 흐름 (바뀐 뒤)

```
[등록 화면] 토글 ON + 방 선택 + 상태 선택
      ↓ POST /wardrobe/uploads/  (shared_room_id, shared_status)
[job]  wardrobe_upload_job.shared_room / shared_status     ← 멤버 검증 통과분만
      ↓ 이미지 처리 콜백
[옷]   wardrobe_item.pending_share_room / _status          ← confirmed=false
      ↓ PATCH /wardrobe/items/{id}/ {confirmed:true}
[공유] shared_wardrobe_item 행 생성 + 예약 컬럼 NULL       ← 응답에 shared_room_id
```

카탈로그에서 고른 옷은 `skip_processing` 이라 3~4단계를 건너뛰고 업로드 응답 안에서 바로 공유된다.
