# Part 1. 발표자 사전 이해 자료

## 1.1 기능 전체 흐름

```
[1] PUT  /body/basic/          성별 · 키 · 몸무게
                               → 사람이 입력한다. AI가 만들지 않는다.
        │
        ├─[2a] POST /body/estimate/    무사진 · 동기 · 1초 미만
        │      모델 3개를 돌려 치수 12개를 만들고, 비율 2개는 나눗셈으로 계산
        │        · hist_gradient_boosting_181            → chest · waist · hip · shoulder
        │        · hist_gradient_boosting_circumference  → thigh · calf · arm
        │        · hist_gradient_boosting_exact_lengths_v2 → 길이 5개
        │
        └─[2b] POST /body/photos/      사진 · 비동기 · 202 + transaction_id
               백그라운드 스레드 → Kimi K2.5가 12개 전부 반환 → 비율 계산
               결과는 GET /body/photos/{transaction_id}/ 로 폴링
        │
[3] PATCH /body/detail/        사용자가 14개 중 원하는 것만 수정
        │
        └→ body_profile.py 가 SizeKorea 분포에 상대화
           → 실루엣(체형 5종) · BMI 밴드 · 비율 밴드 산출 → 추천에 사용
```

**14개 = 치수 12개 + 비율 2개.** 무사진 경로와 사진 경로가 **같은 형태의 응답**을 돌려주므로 앱은 파서를 하나만 두면 된다.

**재추정하면 상세 14개는 최신 추정값으로 덮인다.** 사용자가 PATCH로 고친 값도 마찬가지다. 이것은 의도한 설계다 — 저장된 값은 항상 "가장 최근 추정 결과"이고, 마음에 들지 않으면 사용자가 다시 고치면 된다.

## 1.2 모델을 3개로 나눈 이유

**세 모델은 알고리즘도 같고(HistGradientBoosting) 입력도 같다(성별·키·몸무게).**
나뉜 이유는 알고리즘 차이가 아니라 **12개 컬럼이 한 CSV에 다 들어 있는 표가 없어서**다.

| 담당 출력 | artifact 파일 | 학습 데이터 | 입력 | 왜 따로 만들었나 |
|---|---|---|---|---|
| 가슴·허리·엉덩이·**어깨** | `hist_gradient_boosting_181.joblib` | SizeKorea 8차 **직접측정** 프로필 181명 → **172행** 학습 | 성별·키·몸무게 | 사진 경로와 같은 사람·같은 계측 정의를 쓰려고 |
| 허벅지·종아리·팔뚝 둘레 | `hist_gradient_boosting_circumference.joblib` | 같은 직접측정 계열 **178행** | 동일 | 3D 원천에 이 세 둘레 컬럼이 아예 없음 |
| 길이 5개 | `hist_gradient_boosting_exact_lengths_v2.joblib` | SizeKorea 8차 **3D 측정** 4,545 → **4,485행** | 동일 | 3D에만 랜드마크 높이가 있어 길이를 정의할 수 있음 |

**합칠 수 없는 이유**: 직접측정 181명과 3D 4,485명은 `subject_id` 교집합이 **0명**이다(8개 항목 최근접 L1거리 최소 4.46cm). 같은 사람이 아니라서 한 표로 만들 수 없다.

> "181명만으로 학습했다"는 표현은 **맨 윗줄(코어 둘레 4개)에 대해서만** 맞다.
> `estimate_from_basic()`은 셋을 모두 로드해 결과를 합친다.

## 1.3 길이 5개가 정확히 무슨 데이터인가

전부 **3D 스캔 랜드마크 높이의 차이**다. 그래서 3D 데이터셋에서만 만들 수 있다.

| 필드 | 정의 | MAE | R² |
|---|---|---:|---:|
| `thigh_length` | 샅높이 − 무릎뼈가운데높이 | 1.396 cm | 0.405 |
| `calf_length` | 무릎뼈가운데높이 − 가쪽복사높이 | 1.065 cm | 0.776 |
| `torso_length` | 어깨높이 − 위앞엉덩뼈가시높이(골반점) | 1.660 cm | 0.439 |
| `leg_length` | 위앞엉덩뼈가시높이 − 가쪽복사높이 | 1.537 cm | 0.857 |
| `neck_length` | 턱끝높이 − 목앞높이 | 0.917 cm | 0.256 |

> ⚠️ `neck_length`는 MAE 0.917cm로 가장 좋아 보이지만 **R²가 0.256**이다.
> 키·몸무게로는 사실상 예측되지 않고 집단 평균이 나오는 값이다.
> "목길이 0.917cm"만 강조하면 R²를 물었을 때 곤란하다. 실제 값은 사진 경로로만 얻을 수 있다.

## 1.4 비율 2개는 모델이 아니다

```
thigh_calf_ratio = thigh_length ÷ calf_length     ← 길이 ÷ 길이 (둘레 아님)
torso_leg_ratio  = torso_length ÷ leg_length      ← 길이 ÷ 길이
```

회귀로 학습하지 않고 **서버에서 나눗셈으로 만든다.** 예측 비율을 따로 학습하면 그 값이 같은 응답의 예측 길이와 어긋날 수 있기 때문이다. 계산으로 만들면 사진 경로에서 길이만 덮어써도 비율이 자동으로 따라 움직인다.

| 비율 | MAE | R² |
|---|---:|---:|
| `thigh_calf_ratio` | 0.046 | 0.293 |
| `torso_leg_ratio` | 0.028 | 0.020 |

> MAE는 작지만 R²가 낮다 → **"오차는 작지만 개인차는 못 잡는다."** 이 단서를 함께 말한다.

## 1.5 체형은 무엇을 기준으로 판정하나

기준 파일: `api/apps/recommend/rules/body_shape_thresholds.json` (v4.0.0)
판정 코드: `api/apps/recommend/services/body_profile.py`

체형 정보는 **두 층**으로 나뉜다.

### (1) 가로 체형 5종 — 둘레·폭 4개만 사용

- 기준 데이터: `sizekorea_172_clean.csv` — **172명 (여 81 / 남 91)**, 성별 분리
- 필요 입력: `gender, shoulder, chest, waist, hip` — **비율 2개는 쓰지 않는다**

```
upper_lower      = 0.6 × 어깨백분위 + 0.4 × 가슴백분위 − 엉덩이백분위
waist_definition = 허리 ÷ ((가슴 + 엉덩이) / 2)

우선순위대로 판정:
  waist_definition ≥ p90  → 둥근체형
  upper_lower      ≥ p67  → 역삼각형체형
  upper_lower      ≤ p33  → 삼각형체형
  waist_definition ≤ p33  → 모래시계형체형
  그 외                    → 직사각형체형
```

핵심은 **절대 수치가 아니라 한국인 분포 안에서의 상대 위치**라는 점이다.

### (2) 세로·볼륨 비율 밴드 — 비율 2개 + 목길이

| 지표 | 밴드 |
|---|---|
| `thigh_calf_ratio` | `calf_dominant` / `balanced` / `thigh_dominant` |
| `torso_leg_ratio` | `short_torso` / `balanced` / `long_torso` |
| `neck_length` | `short` / `average` / `long` |

이 밴드의 기준선은 172명이 아니라 **3D 4,485명**에서 뽑았다(`length_threshold_sample_size`).

### 반드시 함께 말할 한계

기준 파일의 `limitations`에 이미 적혀 있다.

> "이미지가 연결된 한국 성인 **172명**(F 81, M 91)의 **내부 기준이며 모집단 대표 규준이 아니다.**"
> "성별 이분 표기(M/F)만 존재해 그 밖의 사용자에게 적용할 검증 근거가 없다."

## 1.6 무사진 모델 선정 벤치마크 (슬라이드 40쪽 근거)

- 데이터: `sizekorea_measurements_clean.csv` **5,092행**
- 분할: 학습 4,092명 / **공통 test 1,000명** (`random_state=42`로 고정 저장)
- 입력: `gender · height · weight` / 출력: 둘레·폭 **7개**
- 기본 모델 4개는 로컬 CPU, HF 모델 3개는 Colab GPU에서 실행

| 순위 | 모델 | 구분 | MAE(cm) | RMSE(cm) | R² | 1건 예측(ms) |
|---:|---|---|---:|---:|---:|---:|
| 1 | knn | 기본 | **1.915** | 2.465 | 0.785 | **0.013** |
| 2 | hist_gradient_boosting | 기본 | 1.920 | **2.461** | **0.786** | 0.170 |
| 3 | random_forest | 기본 | 1.929 | 2.469 | 0.785 | 0.104 |
| 4 | tabpfn_v2 | HF | 1.971 | 2.515 | 0.775 | 9.85 |
| 5 | nori | HF | 1.980 | 2.528 | 0.773 | 19.89 |
| 6 | tabpfn_mix | HF | 2.008 | 2.561 | 0.768 | 3.47 |
| 7 | baseline | 기본 | 4.497 | 5.593 | −0.001 | 0.0001 |

**Hist를 고른 이유**: MAE는 KNN과 0.005cm 차이지만 **RMSE·R² 1위** → 큰 오차가 더 적고 안정적이다.

> ⚠️ **반드시 붙일 각주**: 이 표는 **모델 선정 당시 legacy 7둘레 벤치마크**이며, 현행 서빙 모델의
> 항목별 MAE와 혼용하지 않는다. 이 단서가 없으면 여기의 1.915cm와 22쪽의 허리 3.406cm가
> 충돌하는 것처럼 보인다. (전자는 7개 평균, 후자는 허리 단일 항목)

>
> 사진을 필수로 하지 않은 이유는 비용과 이탈을 줄이기 위해서이며, 이 값은 의료 측정치가 아니라 추천과 사이즈 보조를 위한 추정값입니다."

## 19쪽 — 역할별 모델 선정 (약 1분 5초)

> "하나의 모델이 모든 신체 지표에서 가장 좋지는 않았습니다. 그래서 출력 특성별로 모델을 나눴습니다.

>
> 다만 **알고리즘은 셋 다 HGB이고 입력도 성별·키·몸무게로 같습니다. 모델을 3개로 나눈 건 학습 데이터가 달라서입니다.** 둘레는 직접측정 181명 계열에, 길이 5개는 랜드마크 높이가 있는 3D 4,485명에 있는데, 두 조사는 **동일인 교집합이 0명**이라 한 표로 합칠 수 없었습니다.

>
> 사진 모델은 동일 입력과 동일 평가셋에서 정확도·속도·비용 세 축을 다 측정했지만, **정확도를 우선해 Kimi K2.5를 택했습니다.** 평균 MAE 2.757센티미터로 차순위 3.441보다 나았습니다. Qwen은 0.84센티미터 나쁜 대신 30배 저렴해서, 규모가 커지면 전환하는 경로를 열어뒀습니다."

> 틀린 문장이다(길이끼리만 나눈다). 18쪽에서 이미 정확히 말했으므로 여기서는 빼는 것이 맞다.

# Part 3. 슬라이드 22·23쪽 쉬운 해설

## 22쪽 「역할 별 모델 선정」 — 표를 읽는 법

이 표는 **"어떤 값을, 어떤 모델이, 무슨 데이터로 만들었고, 얼마나 정확한가"**를 한 줄에 하나씩 적은 것이다. 열 이름을 풀면 이렇다.

| 열 이름 | 실제 의미 |
|---|---|
| 담당 출력 | 이 모델이 만들어 내는 값이 무엇인가 |
| 사용 모델 | 그 값을 만드는 파일 이름 |
| 무엇을 보고 평가? | **어떤 데이터 몇 명으로 채점했는가** |
| 검증 결과 | 채점 점수 (cm 단위, 낮을수록 좋음) |
| 채택 이유 | 왜 이 모델을 골랐는가 |

### 줄별로 풀어 쓰면

**1행 · 코어 둘레 4 / HGB 181**
가슴·허리·엉덩이·어깨를 만드는 모델이다. 실제로 줄자로 잰 172명으로 채점했고, 가슴은 평균 3.043cm, 허리는 3.406cm 틀렸다.
→ *"5-Fold MAE"* = 데이터를 5조각으로 나눠 4조각으로 배우고 1조각으로 시험 보기를 5번 반복한 평균 점수. 한 번만 시험 보면 운이 좋을 수 있어서 5번 한다.

**2행 · 부가 둘레 3 / circumference**
허벅지·종아리·팔뚝 둘레를 만드는 모델이다. 178명으로 채점했고 오차는 1.170~2.223cm였다.

**3행 · 길이 5 / exact_lengths_v2**
허벅지길이·종아리길이·몸통길이·다리길이·목길이를 만드는 모델이다. 3D 스캔 4,485명으로 채점했고 오차는 0.917~1.660cm였다.
→ *"3D 파생"* = 3D 스캐너가 잰 **높이 값들을 빼서** 만든 길이라는 뜻.

**4행 · 사진 추정 / Kimi K2.5**
사진 두 장을 보고 값을 만드는 AI다. 두 가지를 봤다.
- *A/B MAE 143명* — 사진과 무사진 중 어느 쪽이 나은지 143명으로 비교
- *배치 평가 145건* — 145명 전부 응답에 성공(145/145)
- *핵심3 평균 3.126* — 가슴·허리·엉덩이 세 부위 평균 오차

**맨 아래 문장**
"비율 2개는 모델 평가 대상이 아니라, 길이 예측 결과의 서버 나눗셈 후처리입니다"
= 허벅지:종아리 비율과 상하체 비율은 **AI가 맞힌 값이 아니라 나눗셈 결과**라서, 채점표에 넣지 않았다는 뜻이다.

### 한 문장 요약

> 값의 종류마다 쓸 수 있는 원본 데이터가 달라서 모델을 셋으로 나눴고, 각각 자기 데이터로 채점했다.

## 23쪽 「운영·API 검증」 — 숫자 4개와 API 목록

### 위쪽 숫자 카드 4개

| 숫자 | 무슨 뜻인가 |
|---|---|
| **145 / 145** | 145명 사진을 넣었더니 **145번 다 성공**했다 (실패 0건) |
| **10.828초** | AI가 사진을 보고 답을 주기까지 **평균 10.8초** 걸렸다 |
| **$0.005102** | 한 번 부를 때마다 **약 5원**이 든다 |
| **202** | "접수했습니다"라는 뜻의 HTTP 응답 코드 |

**202가 왜 중요한가**: 사진 분석이 10초 넘게 걸리는데 그동안 앱을 멈춰 두면 사용자는 앱이 멈춘 줄 안다. 그래서 서버가 먼저 **"접수했어요, 번호표 드릴게요"(202 + transaction_id)**라고 답하고, 앱이 그 번호로 "다 됐나요?"를 물어보는 방식이다. 식당 진동벨과 같다.

### 아래쪽 운영 API 5줄

| API | 하는 일 | 쉬운 말 |
|---|---|---|
| `POST /body/estimate/` | 무사진 추정 (동기) | 키·몸무게만으로 바로 계산 |
| `POST /body/photos/` | 사진 접수 (비동기) | 사진 내고 번호표 받기 |
| `PATCH /body/detail/` | 상세 치수 수정 | 내가 직접 고치기 |
| `GET /body/` | 신체치수 조회 | 지금 저장된 값 보기 |
| `GET /body/photos/{transaction_id}/` | 트랜잭션 결과 조회 | 번호표로 결과 찾기 |

**오른쪽 「데이터 계약」 박스**
- *source enum: basic_info · photo* — 이 값이 **사진 없이 나온 건지, 사진으로 나온 건지** 표시하는 꼬리표다. 앱이 화면에 "키·몸무게로 추정한 결과예요" / "사진과 입력 정보로 추정한 결과예요"를 구분해 보여줄 수 있다.
- *사진 작업 동시성 제어* — 한 사람이 사진을 연달아 올려 서버를 여러 번 돌리지 못하게 **진행 중인 작업을 1건으로 제한**했다는 뜻이다.

### 한 문장 요약

> 오래 걸리는 사진 분석은 번호표 방식으로 처리했고, 145건 전부 성공했으며, API는 용도별로 나눠 두었다.

# Part 4. 예상 질문 대비

| 질문 | 답변 |
|---|---|
| "1.915cm랑 허리 3.406cm 중 뭐가 맞나요?" | 둘 다 맞습니다. 앞은 **모델 선정 당시 7둘레 평균**, 뒤는 **현행 서빙 모델의 허리 단일 항목**입니다. 기준이 다릅니다. |
| "왜 모델을 3개나 쓰나요?" | 알고리즘은 같습니다. 원본 데이터가 달라서입니다. 직접측정 세트에는 길이 랜드마크가 없고, 3D 세트에는 팔뚝·종아리·허벅지 둘레가 없습니다. 두 세트는 동일인 교집합이 0명입니다. |
| "무슨 근거로 모래시계형이라고 하나요?" | SizeKorea 실측 **172명**의 성별 분포에서의 상대 위치입니다. 172명 내부 기준이라 모집단 규준은 아니라는 점을 함께 밝힙니다. |
| "목길이 오차가 제일 작던데요?" | MAE는 0.917cm로 작지만 **R²가 0.256**입니다. 키·몸무게로는 예측되지 않아 사실상 집단 평균이고, 실제 값은 사진 경로로만 얻습니다. |
| "사진이 항상 더 정확한가요?" | 아닙니다. **가슴·허리에서만 확실히 낫고** 나머지는 무사진이 낫습니다. 그런데 그 두 부위가 상·하의 사이즈를 정하므로 옷 추천 목적에서는 가장 중요한 개선입니다. |
| "사용자가 고친 값은 보존되나요?" | 재추정하면 최신 추정값으로 덮입니다. 저장값을 항상 "가장 최근 추정 결과"로 두려는 의도된 설계이고, 이후 다시 수정할 수 있습니다. |
| "사진은 저장하나요?" | 저장하지 않습니다. 요청에서 바이트로 읽어 추론에만 쓰고 버립니다. |
| "Kimi가 제일 느리고 비싸지 않나요?" | 맞습니다. 속도는 Grok보다 느리고 비용은 Qwen보다 30배 비쌉니다. **정확도를 우선한 선택**이며, 규모가 커지면 Qwen 전환 경로를 열어뒀습니다. |
